# 90-day launch plan

## Outcome

At day 90, UofC should have a safe, repeatable pilot system—not maximum client count:

- 3–5 students;
- 3 active small-business clients;
- at least 2 narrow tools in real use;
- one shared module used by more than one client;
- a documented discovery-to-support workflow;
- clear adult supervision, access, recording, and production policies;
- three pilot episodes of “Home Schooled.”

## Days 1–15: define the container

- appoint one program owner and one production/security owner;
- choose the first student cohort and confirm guardian consent;
- define approved communication channels and adult visibility;
- classify data that students may and may not handle;
- create one-page templates for discovery, scope, acceptance, and launch review;
- choose one initial vertical and three prospects;
- verify the podcast’s title availability, guest identities, and visual-setting decision.

**Gate:** no client data or production access until supervision and access rules are written.

## Days 16–30: discovery and foundations

- teach terminal, Git, collaboration, AI-tool use, and safe credential practices;
- run supervised client interviews;
- document current workflows and baseline time/cost;
- qualify pilots with the opportunity rubric;
- select two projects with narrow acceptance criteria;
- record one private podcast test and review pacing, warmth, and question quality.

**Gate:** every build has a named client owner, non-goals, safe test data, and a senior reviewer.

## Days 31–50: prototype

- build with synthetic or sanitized data;
- hold weekly client-use sessions;
- track every request as a proposed scope change;
- add authentication, audit history, error reporting, and rollback before launch;
- identify one shared component across the two builds;
- record the first two publishable podcast pilots.

**Gate:** the client completes the target workflow unassisted and approves the acceptance criteria.

## Days 51–70: controlled production

- deploy to one to five users per client;
- establish a support channel and severity definitions;
- review adoption and failures weekly;
- keep students as the visible product owners while senior engineers retain production control;
- deploy the shared module for a second client only if the workflows genuinely match.

**Gate:** no high-severity unresolved issue and a tested rollback/offboarding process.

## Days 71–90: evaluate and decide

- measure usage, time saved, incident load, client satisfaction, and student autonomy;
- calculate actual support hours per client;
- decide whether each project should stop, remain bespoke, or become a reusable vertical module;
- document curriculum changes based on observed gaps;
- publish three “Home Schooled” episodes on a consistent schedule;
- choose the next cohort and client load from evidence.

## Weekly operating rhythm

- **Monday:** student portfolio review and risk triage;
- **Tuesday–Wednesday:** client discovery, building, and testing;
- **Thursday:** production review and supervised deployment;
- **Friday:** demos, reflection, curriculum update, and reusable-module review.

## First artifacts to create

- client discovery brief;
- one-page scope and non-goals;
- data and access checklist;
- production-readiness checklist;
- change request and approval record;
- incident and escalation guide;
- weekly client status update;
- student reflection and skills rubric;
- podcast guest brief and release form.
